# Dependency Vulnerability Scanning

How `alfresco-collabora-online` detects known CVEs in its Java dependencies, and
why the pipeline blocks on some of them and not others.

## Why two perimeters

The Maven reactor ships two Java artefacts, and neither carries third-party code:

- `collabora-platform-extension` builds an **AMP** for the repository. An AMP
  only packages `compile` scope dependencies; Alfresco itself, Spring, Jackson
  and the rest are `provided` by the ACS image at runtime. The `lib/` folder of
  the last built AMP (1.8.0) holds a single JAR, the module's own
  `collabora-platform-extension-1.8.0.jar`.
- `collabora-share-extension` builds a plain JAR loaded by Share. Its only
  dependency, the Share classes, is `provided`.

The `compile` perimeter is therefore what we ship and own, and today it is
limited to our own two artefacts. The `provided` perimeter is the ACS platform
and the Share web application, which this repository cannot fix.

| SBOM | Scopes | Contents | Gate |
|---|---|---|---|
| `target/bom-runtime.json` | `compile` | Our two artefacts, plus any library a module adds later | **Fails the pipeline on CRITICAL** |
| `target/bom-full.json` | `compile` + `provided` | The above plus ACS and Share | Reported, never blocking |

The gate exists for the day a module declares a `compile` dependency.

## Running it locally

```bash
mise run audit        # blocking gate, same as CI
mise run audit:full   # full runtime tree, HIGH + CRITICAL, informative
mise run sbom         # regenerate both SBOMs only
```

`mise` provides both Maven and the Trivy version pinned in `mise.toml`. That
version is kept in sync with the image tag used by the `dependency-scan` job in
`.gitlab-ci.yml`, itself mirrored in `images-docker/sync-images-docker/sync.yaml`.

## How it works

SBOMs are generated by the CycloneDX Maven plugin, declared in the root
`pom.xml` under `<pluginManagement>` and **not bound to any lifecycle phase**:
a normal `mvn package` is unaffected. It is invoked explicitly:

```bash
mvn org.cyclonedx:cyclonedx-maven-plugin:makeAggregateBom \
    -DoutputFormat=json -DoutputName=bom-runtime \
    -DincludeProvidedScope=false -DincludeTestScope=false
```

> The plugin's user properties have **no `cyclonedx.` prefix** (`-DoutputName`,
> not `-Dcyclonedx.outputName`). Getting this wrong silently produces a default
> `bom.json` with every scope included, and the scan then reports on the wrong
> perimeter without failing.

`makeAggregateBom` walks the reactor, so it needs no prior build. It refuses to
run with `-o` ("Goal requires online mode"), even when every artefact is in the
local repository.

Trivy then scans the SBOMs. It needs no NVD API key, unlike OWASP
dependency-check, which is why it was chosen here.

## CI

No pipeline runs on `stable`: a release is built and published by the pipeline
of its version tag (`1.8.0`). The `vue/*` and `aca/*` tags, which release the npm
packages, create no pipeline. Stage `security`, ahead of `deploy`, runs on
`develop` and on version tags:

- **`sbom`** (Maven image) - generates both SBOMs, published as artifacts.
- **`dependency-scan`** (Trivy image) - scans them. The full report is printed
  first for context, then the runtime SBOM is re-scanned with `--exit-code 1
  --severity CRITICAL`. Raw JSON reports are kept as artifacts (`when: always`).

`maven-deploy`, the only publishing job, lists `dependency-scan` in its `needs`.
Stage ordering alone would hold it back today, but jobs using `needs` start as
soon as their listed dependencies succeed and otherwise **ignore preceding
stages entirely**: naming the scan keeps the gate in place whatever is added to
that list later. `maven-deploy` consumed no artifact from an earlier job (it
was the only job), so nothing else had to be listed. The need is `optional`
because the scan does not run on feature branches, where a mandatory need would
stop GitLab from creating the pipeline.

The Trivy vulnerability database is cached under `.trivycache/` with its own
cache key, which overrides the global `.m2` cache for that job.

## Release SBOM

On a version tag, once `maven-deploy` has published the release, `sbom-publish`
publishes the two SBOMs the gate scanned to Nexus next to it, with
`deploy:deploy-file`:

| File | Classifier |
|---|---|
| `bom-runtime.json` | `cyclonedx` |
| `bom-full.json` | `cyclonedx-full` |

The two `deploy-file` executions (`sbom-runtime`, `sbom-full`) are declared in
the root `pom.xml` with `<phase>none</phase>`, so `mvn deploy` never runs them.
They target `sbom.repository.id` / `sbom.repository.url`, which default to the
release repository of `<distributionManagement>`; the pom version at the tag
must therefore be a release version. A dry run against a local folder:

```bash
mise run sbom
mvn -N deploy:deploy-file@sbom-runtime deploy:deploy-file@sbom-full \
    -Dsbom.repository.id=local -Dsbom.repository.url=file:///tmp/fake-nexus
```

A released version can then be re-scanned at any time against the current
vulnerability database, from its published SBOM.

## Remediating a finding

**In the runtime SBOM** (blocking) - it is our dependency: fix it in the
`pom.xml` of the module that declares it (`collabora-platform-extension` or
`collabora-share-extension`), by bumping or excluding the library.

**In the full SBOM** (informative) - it belongs to the platform. Two options, in
order of preference:

1. Bump `alfresco.platform.version` (ACS) or `alfresco.share.version` (Share)
   in the root `pom.xml`.
2. Override the JAR in the platform Docker image. `alfresco-mmt` **never
   overwrites** a JAR already present in the platform, it only adds, so
   shipping a newer version through an AMP does not work.

The `<dependencyManagement>` pin on BouncyCastle in the root `pom.xml` only
constrains compilation, and the full SBOM reports that pinned version (1.83),
not necessarily the one ACS loads at runtime.

## Not covered here

This scans the Maven reactor only. The npm packages `collabora-aca-extension`
and `collabora-vue-component` are not part of it. CVEs in the JRE, Tomcat and
the OS packages of the ACS and Share images, and in the Collabora Online image,
are found with `trivy image` against the built images, which belongs to the
image build pipeline rather than to this dependency scan.
